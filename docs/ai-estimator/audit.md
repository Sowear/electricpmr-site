# Технический аудит и статус ИИ-помощника

Дата аудита: 2026-10-26

## Фактическая архитектура

- Приложение собрано на Astro 6 с React 18 и React Router; пакетные зависимости управляются `package-lock.json` (есть также `bun.lockb`). Команда production-сборки — `npm run build`.
- Основная клиентская модель доступа называется Supabase и типы описаны в `src/integrations/supabase/types.ts`. При этом клиентский адаптер в `src/integrations/supabase/client.ts` направляет запросы через собственный Worker API в Cloudflare/D1; прямой Supabase JS клиент является fallback при наличии публичных переменных.
- Схема текущего D1 развёртывания описана в `cloudflare/schema.sql`; проект также хранит Supabase миграции. Эти две схемы нельзя считать автоматически синхронизированными.
- Существуют сущности смет и строк: `estimates`, `estimate_line_items`, `estimate_history`; каталог: `catalog_items`. PDF реализован в `src/lib/pdfGenerator.ts` и `src/lib/pdfDocumentGenerator.ts`. Ручной редактор и обычное сохранение уже существуют.
- Цены смет фиксируются в строках `unit_price`; расчёт строки и итогов реализован в `src/types/estimator.ts` и дублируется на стороне Cloudflare Worker.
- Hooks `useLineItemPresets` и CRUD каталога используют серверную таблицу `catalog_items`. Для пользователей, у которых старые позиции находятся в `localStorage`, экран каталога предлагает явный разовый импорт с пропуском совпадающих названий. Локальное хранилище не удаляется автоматически.
- Авторизация Worker получает пользователя и роли из сессии; права управления проверяются ролями `manager`, `admin`, `super_admin`. У смет есть роли и правила редактирования/статусы в UI.
- Firebase в исходном проекте не обнаружен. Живую схему или реальные данные удалённой БД в ходе аудита не запрашивал; отчет опирается на локальную схему и миграции.

## Добавленная первая версия

- `/estimator/assistant` — защищённый по серверной роли экран подготовки черновика, редактирования объёмов/удаления строк и подтверждения сохранения.
- `POST /api/ai-estimator/draft` — маршрут Cloudflare Worker. Он передаёт модели только описание объекта и до 300 активных позиций каталога; цены в ответе модели не принимаются. После ответа сервер сопоставляет ID с выборкой каталога, берёт `base_price` из D1 и сам считает сумму строки.
- `POST /api/ai-estimator/save` — сервер повторно проверяет доступные ID, количества и повторяющиеся названия работ, повторно загружает текущие цены из каталога, создаёт шапку и строки в одной D1 batch-транзакции, сохраняет контекст осмотра и запись `ai_draft_created` в истории, затем пересчитывает итоги. Клиент не может записать произвольную цену через этот путь.
- `POST /api/ai-estimator/add-lines` — применяет только явно подтверждённые добавления к черновику/отправленной смете. Цены повторно берутся из каталога; повтор существующей позиции и изменение согласованной сметы блокируются.
- Неизвестные объёмы возвращаются как `null`, UI требует заполнить их или удалить строку. Сохранение выполняется после нажатия пользователем кнопки и использует существующие `estimates` и `estimate_line_items` через текущие hooks. Цены каталога не меняются.
- `estimate_ai_context` хранит исходное описание и структурированный контекст осмотра созданной ИИ-сметы. Он отображается в редакторе после сохранения. Для новой базы таблица включена в `cloudflare/schema.sql`; для существующих D1/Supabase окружений подготовлены отдельные миграции.
- Новая схема БД и миграция не нужны. Существующие исторические сметы не модифицируются.

## Ограничения и риски

- Нужен доступный Cloudflare Worker, совпадающий с `VITE_API_BASE_URL`, и Cloudflare secret `OPENAI_API_KEY`; при необходимости — переменная `OPENAI_MODEL`. Без ключа API корректно возвращает 503. API-вызов не проверен живым запросом: ключ и доступ к Cloudflare окружению не предоставлены.
- Реализован только первый шаг ИИ-сметчика: разбор описания, подбор каталожных работ и сохранение подтверждённого черновика. Интерактивное редактирование сметы диалогом, история предложений ИИ, MCP/ChatGPT-коннектор, рыночный поиск, материалы, голос/фото, аналитика завершённых заказов и полноценный общий контекст осмотра пока не реализованы.
- Роли и права Worker проверяются по текущей сессии. Перед внешней эксплуатацией необходимо проверить конфигурацию production Worker и Cloudflare секретов; локальная сборка сама по себе не подтверждает его развёртывание.
- В `catalog_items` есть `market_min`/`market_max`, но seed может генерировать их как 70%/130% от base price. Эти значения не используются как проверенные рыночные наблюдения.
- Текущий Worker формирует CORS `*`; запрос с авторизацией в основном браузерном приложении обычно same-origin, но политика требует отдельного hardening до внешнего API/MCP использования.
- Запись атомарна в текущем D1 Worker через `DB.batch`; deployment с прямым Supabase fallback не использует этот Worker endpoint, поэтому новая функция там недоступна без развёрнутого API. В существующую D1 базу необходимо применить `cloudflare/migrations/0001_estimate_ai_context.sql`.

2. Добавить историю диалоговых предложений и изменений сметы с версионированием/аудитом и явным snapshot цены.
3. Расширить контекст объекта до отдельных замеров и модулей материалов, рынка и завершённых заказов с раздельными источниками данных.
4. Добавить историю диалоговых правок и голос/фото только после определения безопасного хранения/удаления.
5. Выбрать механизм MCP/ChatGPT с поддерживаемой аутентификацией; не выдавать произвольный доступ к таблицам и требовать подтверждения записи.
6. Добавить тесты для соответствующих доменных правил и серверных прав доступа.
